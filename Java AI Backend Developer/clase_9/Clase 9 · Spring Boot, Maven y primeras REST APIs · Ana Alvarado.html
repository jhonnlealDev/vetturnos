Spring Boot: de una necesidad de negocio a una API REST viva

Construiremos gestor-productos: un backend Java capaz de listar y crear productos mediante HTTP, entendiendo qué resuelve Spring Boot, cómo Maven organiza el proyecto y por qué una arquitectura por capas hace que el código pueda crecer.

01PROBLEMA REAL

Una aplicación móvil necesita hablar con nuestro código Java

Punto de partida

¿Quién abre el servidor, escucha peticiones, interpreta la URL, convierte JSON en objetos Java y construye la respuesta?

Una tienda online necesita dos capacidades mínimas: consultar su catálogo y registrar nuevos productos. El problema no es solamente escribir una clase Producto. Debemos exponer esa lógica para que una app móvil, una página web o cualquier otro cliente pueda usarla por internet.

CLIENTEApp móvilSolicita o envía datos
HTTP →
BACKENDSpring BootRecibe, procesa y responde
→ JSON
RESPUESTAProductosLista o confirmación

Objetivo del producto

API de Productos

GET /api/productos devolverá el catálogo. POST /api/productos recibirá un producto nuevo y lo guardará temporalmente en memoria.

Decisión técnica

¿Tiene sentido programar desde cero el servidor y toda la infraestructura HTTP en cada proyecto?
No. Es trabajo repetitivo, complejo y propenso a errores. Un framework resuelve esa infraestructura común para que el equipo se concentre en las reglas específicas del negocio.
02FRAMEWORK

Spring Boot elimina la “plomería” del backend

Definición técnica

Spring Boot es un framework de Java para construir aplicaciones backend, especialmente APIs REST, con servidor integrado y autoconfiguración.

En palabras sencillas

Nos entrega una base profesional ya preparada. Nosotros escribimos las reglas de nuestro negocio; Spring se encarga de gran parte de la infraestructura.

Analogía

Es como alquilar un restaurante con cocina, gas, agua y electricidad instalados. El equipo llega a cocinar su menú, no a construir el edificio.

Sin framework

  • Configurar servidor manualmente
  • Interpretar HTTP
  • Convertir formatos
  • Resolver integración entre piezas

Con Spring Boot

  • Servidor embebido
  • Rutas mediante anotaciones
  • Conversión automática JSON ↔ Java
  • Convenciones profesionales

Criterio profesional

“Escribir menos código” no es el objetivo principal. El valor real es dejar de reimplementar infraestructura repetitiva y concentrarnos en el código que diferencia al negocio.

03DEPENDENCIAS

Maven trae, conecta y construye las herramientas del proyecto

Cómo imaginarlo

Maven funciona como una lista de mercado inteligente: pedimos Spring Web y Maven descarga esa dependencia junto con todo lo que necesita internamente.

Herramienta

Maven gestiona dependencias y automatiza la construcción de proyectos Java.

Archivo central

pom.xml declara identidad del proyecto, versión de Java y librerías requeridas.

Resultado

El equipo puede clonar el repositorio y reconstruir el mismo entorno sin compartir archivos .jar manualmente.

DEPENDENCIApom.xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>

Antes de agregar librerías

¿Por qué hoy no agregamos una dependencia de base de datos?
La clase trabaja con datos en memoria. Agregar dependencias sin usarlas aumenta complejidad, ensucia el proyecto y puede activar configuraciones que todavía no existen. La regla es: incluir solamente lo que el sistema necesita ahora.

06DISEÑO

Separar responsabilidades permite que el backend crezca

Antes de escribir las clases, definimos dónde vive cada responsabilidad. El objetivo no es crear carpetas por estética, sino reducir acoplamiento y hacer que cada cambio tenga un lugar predecible.

ENTRADA HTTPcontroller

Recibe GET y POST, valida la ruta y construye la respuesta.

↓ delega
NEGOCIOservice

Decide cómo listar, guardar o buscar productos.

↓ usa
DATOSmodel

Define qué es un producto y qué información contiene.

Analogía del restaurante

Cada rol tiene un trabajo

El controller es el mesero que recibe el pedido; el service es la cocina que ejecuta la operación; el model representa los ingredientes y platos con los que se trabaja.

Responsabilidad única

Si todo podría funcionar dentro de una sola clase, ¿por qué dividirlo?
Porque un sistema profesional cambia constantemente. Separar capas permite modificar la lógica sin alterar las rutas HTTP, probar cada parte de forma aislada y localizar errores con mayor rapidez. Es una aplicación práctica del principio de responsabilidad única.
07MODEL

Producto representa los datos que viajarán por la API

Qué vamos a hacer

Crear una clase Java que represente un producto.

Por qué lo hacemos

Spring necesita una estructura concreta para convertir el JSON recibido y producir el JSON de respuesta.

Qué aprenderás

Cómo el modelo conecta los datos externos con objetos Java.

08SERVICE

El servicio contiene las operaciones del negocio

Qué vamos a hacer

Crear una lista en memoria y dos operaciones: listar y agregar.

Por qué lo hacemos

El controller no debe contener reglas de negocio ni administrar directamente los datos.

Qué aprenderás

Cómo Spring administra un servicio y cómo una capa delega trabajo a otra.

CREARsrc/main/java/com/devsenior/gestorproductos/service/ProductoService.java
package com.devsenior.gestorproductos.service;

import com.devsenior.gestorproductos.model.Producto;
import org.springframework.stereotype.Service;
import java.util.ArrayList;
import java.util.List;

@Service
public class ProductoService {

    private List<Producto> productos = new ArrayList<>();

    public List<Producto> listarProductos() {
        return productos;
    }

    public Producto agregarProducto(Producto producto) {
        productos.add(producto);
        return producto;
    }
}
@Service

Registra la clase como componente administrado por Spring.

List<Producto>

Almacena temporalmente los productos mientras el servidor esté encendido.

listar / agregar

Expone operaciones claras sin revelar cómo se guardan internamente los datos.

Persistencia temporal

Qué ocurre: al apagar o reiniciar la aplicación, la lista vuelve a estar vacía.

Cómo leerlo: no es un error de Spring; es una consecuencia de guardar información únicamente en memoria RAM.

Cómo se resolverá: en la siguiente clase se reemplazará la lista por una base de datos con JPA, Hibernate y una capa repository.

09GET

El controller abre la primera puerta pública de la API

Qué vamos a hacer

Crear el endpoint GET /api/productos.

Por qué lo hacemos

La aplicación cliente necesita una dirección estable para consultar el catálogo.

Qué aprenderás

Cómo las anotaciones conectan una petición HTTP con un método Java y cómo funciona la inyección de dependencias.

CREARsrc/main/java/com/devsenior/gestorproductos/controller/ProductoController.java
package com.devsenior.gestorproductos.controller;

import com.devsenior.gestorproductos.model.Producto;
import com.devsenior.gestorproductos.service.ProductoService;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;
import java.util.List;

@RestController
@RequestMapping("/api/productos")
public class ProductoController {

    private final ProductoService productoService;

    public ProductoController(ProductoService productoService) {
        this.productoService = productoService;
    }

    @GetMapping
    public List<Producto> obtenerProductos() {
        return productoService.listarProductos();
    }
}
GEThttp://localhost:8080/api/productos
↓
200 OK · application/json
[]

Endpoint

Combinación de un método HTTP y una ruta que expone una operación concreta de la API.

Inyección

El controller no crea el service con new; Spring entrega la instancia por el constructor.

Resultado inicial

[] significa “lista válida sin elementos”. La ruta funciona aunque todavía no existan productos.

10POST

POST recibe un JSON y lo convierte en un Producto

GET entrega información. POST recibe información nueva. Ambos usan la misma ruta base, pero representan operaciones distintas porque emplean métodos HTTP diferentes.

AGREGARProductoController.java · imports
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
AGREGARProductoController.java · debajo de obtenerProductos()
@PostMapping
public Producto crearProducto(@RequestBody Producto producto) {
    return productoService.agregarProducto(producto);
}

Prueba completa

Después del POST, repite el GET. La lista debe contener el producto recién creado. Esa secuencia confirma que las capas están conectadas de extremo a extremo.

11DIAGNÓSTICO

Una anotación ausente puede producir datos silenciosamente incorrectos

Experimento controlado

¿Qué sucede si quitamos @RequestBody, aunque el JSON enviado sea correcto?

PROVOCAR ERRORProductoController.java
@PostMapping
public Producto crearProducto(Producto producto) {
    return productoService.agregarProducto(producto);
}
1El cliente envía JSON

Los datos sí viajan en el cuerpo HTTP.

2Falta la instrucción

Spring no sabe que debe leer ese cuerpo como Producto.

3Objeto vacío

Se crea con valores predeterminados: null, 0.

Cómo diagnosticarlo

Síntoma: la petición responde, pero el objeto guardado tiene campos vacíos.

Causa: el parámetro no está vinculado al cuerpo de la petición.

Corrección: restaurar @RequestBody Producto producto.

Lección clave

Las anotaciones no son decoración. Son metadatos ejecutables que le indican a Spring cómo debe tratar clases, métodos y parámetros.

Puente a la Clase 10

¿Cómo hacemos que los productos sobrevivan al reinicio?

La lista en memoria será reemplazada por persistencia real. Aparecerán JPA, Hibernate y una cuarta capa: repository.

LISTA EN MEMORIA→BASE DE DATOS

Pregunta final

¿Qué tendría que cambiar en el service para que los productos no se pierdan al apagar el servidor?
La lógica ya no puede depender de una lista local. Necesita delegar el almacenamiento a una capa especializada que se comunique con una base de datos. Esa capa será el repository.
